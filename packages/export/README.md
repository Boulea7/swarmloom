# @swarmloom/export

Deterministic video and audio export for SwarmLoom: the CLI's render page, the same export inside a web page (`@swarmloom/export/browser`), and a quick in-browser recorder.

## Render page (used by the CLI)

`dist/render/index.html` is a headless page, also exported as `@swarmloom/export/render/*`. Its build also writes `dist/render.sources.json`, the hashes of the workspace files and lockfile it was built from; the CLI build uses it to rebuild a stale page. It sets `window.__swarmloom` and marks `<html data-swarmloom="ready">`. A driver such as the `swarmloom render` CLI over CDP calls:

1. `init({ input, width, height, fps, seed?, agents?, speed?, theme?, labels?, overlays?, sound?, finale?, locale?, tail?, opening?, live?, liveTop?, follow?, intro?, reducedMotion?, bpm?, beatSync?, pack?, cues?, terminalFont?, blueprint? })`, which returns `{ estimatedMs, layers, blueprintSha256 }`.
   - `blueprintSha256` hashes the blueprint JSON after replacing what changes from run to run: the directory the input was served from becomes `input:/`, each `blob:` URL becomes `blob:sha256-` plus the hash of its bytes, and other addresses on the render page's own origin (such as footnote links resolved against the page) start with `page:/`. Remote URLs stay. The same input gives the same hash.
   - `overlays` is `full` (default), `minimal` (no size badges, distance labels, guide lines or rulers) or `none` (cursors, name tags and content only).
   - `opening` (ms, default 0) shows the finished content this long before the intro, then fades it into the blank canvas.
   - `liveTop` (default `false`): going live glides the view back to the top first.
   - `intro` is `true` (default: the warp around the file icon), `"outline"` (a few cursors draw the largest shapes before the swarm joins) or `false` (none).
   - `cues` is a list of `{ at, action, speed? }`: at video time `at` ms the player does `pause`, `resume`, `finish`, `live` or `speed`, which sets the build speed to `speed` (0.05..16) from then on.
   - `terminalFont` is `fit` (default: terminal recordings use 14 px and shrink it to fit the width) or `fill` (the font grows until the window fills the frame's width or height).
   - `input` is `{ name, type?, base64? | text? | url? }`. If `type` contains a slash it is a MIME type; otherwise it is an adapter id or extension that overrides detection.
   - `blueprint` (optional) is a blueprint the driver already captured, such as the CLI's live snapshot of a web page. It is played as is and `input` is not loaded.
   - The player runs inline at `width` x `height` on a `VirtualClock`, with controls off.
2. `step(1000 / fps)` advances the clock in engine ticks of 1/120 s (plus a short tick to a frame time between two ticks), waits for `player.ready()` (fonts, images, decode) after each and for the page's next animation frame (the next two at a device scale factor other than 1, 2 or 4, by which time the browser has rastered the step), and returns `{ state, built, total, done }`. Take a screenshot after each step until `done`. A run is done once the build has finished and `tail` ms (default 2500, 3700 with `liveTop` for the glide back to the top) have passed; a go live still under way then runs on until the stage shows the page. Because the engine ticks at a fixed rate, frame rates that divide 120 (15, 24, 30, 60, ...) show one build.
   - Go live: unless `live` is `false` or `reducedMotion` is on (which keeps the end state), the player goes live once the finale settles, as the toolbar's go live does. The cursors leave and the stage becomes the finished page. An HTML document is loaded with the adapter's `keepLive` frame at the frame height, and that real page is shown over the stage at the same scroll position, on the canvas colour a browser tab paints under it (`Canvas`), so a page without a background of its own never lets the stage under it show through; animations the page started after the capture froze it (in `content-visibility: auto` sections the browser laid out later) are frozen by the same rule then, finite ones at their end and loops half a cycle in. From then on every step pauses all Web Animations (the page, every stage subtree, the live page and its open shadow roots) and the live page's SVG documents and seeks them to the frame time, so the tail never depends on wall time; a transition or animation a seek starts (an inherited value or a container query that changed with it) plays from its start at that frame time, and so does one the page's next rendering update starts (state the engine takes only there: a scroll-state query that sticks a header once go live scrolls the page, the fallback an anchor-positioned tooltip flips to, the link a scroll spy marks current once a seek moves the sections), except that on the frame that went live it plays from the go-live time, which can be engine ticks before the frame: the go-live scroll set it off, and a frame then shows what the same time shows at any frame rate. For those the step waits for that update before it returns, on the frame that went live and, on a page whose styles hold scroll-state queries, `position-try` fallbacks, scroll-spy selectors (`:target-current`, `:target-before`, `:target-after`) or `::scroll-button()` rules (or a sheet of another origin, which cannot be read), on every frame after it: one display frame more per frame there, and one more after each update that started a transition or animation, since seeking it can start another at the update after (three at most; none in a hidden tab, which takes no rendering updates). `<marquee>` elements on the live page, which no seek reaches, hold their resting pose, and its animated `<img>` elements (SVG, GIF, APNG, WebP or AVIF the render page can read) show still copies from `stillImageSource` (@swarmloom/core), swapped in during `init()`; animated CSS images of its elements (backgrounds, masks, border images, list markers, not pseudo-elements) are overridden inline with the same copies (`holdAllCssImages`), and so are the images its inline SVG embeds (`<image>`, `<feImage>`: `holdSvgImages`), its video posters and its image buttons (`<input type="image">`). SVG SMIL replays (`createSvgAdapter({ liveClock: "player" })`) and Lottie players (`createLottieAdapter({ liveClock: "player" })`) follow player time themselves. The same input, options and seed give the same frames.
3. `audioWav(durationMs?)` returns the run's sound log rendered offline to a 48 kHz stereo WAV, as base64. The last frame stays up for one more frame, so first `step()` through that interval without a screenshot (its sounds then join the log, and rates that divide 120 get one soundtrack), then pass the video's length (frames * 1000 / fps); the default is the elapsed time.
   - `soundLog()` returns that log and `scrollLog()` each stretch of scrolling so far (`{ t, end, from, to }`: the tour, a go-live glide), both on the frames' clock. Read `scrollLog()` before the step past the last frame, whose view no frame shows.
4. `dispose()`.

Invalid `init` options reject with a `TypeError` that names the field. Recoverable player errors do not stop a render; the page logs them with `console.warn`. Only one render can be active per page.

## Library

- `exportFrames(playerOptions, { fps, onFrame, tailMs?, maxDurationMs?, onWarning?, signal? })` runs a player on a `VirtualClock`. It calls `onFrame(index, timeMs)` for each frame once the frame's assets are ready, and returns `{ frames, durationMs, soundLog, warnings }`. Frame `n` shows engine time `n * 1000 / fps`; the engine ticks 120 times a second at any frame rate, as on the render page. Player `error` events (skipped layers, a failed layer task, sound) are recoverable: they go to `onWarning` and `warnings` and the export goes on. Throw from `onWarning` to abort instead.
- `renderAudioWav(soundLog, durationMs, options?)` renders sound events to WAV bytes with `OfflineAudioContext`.
- `RenderSession` is the clock-and-player stepping used by both of the above. With `tickRate` (both pass 120) each step advances in ticks on that fixed grid, so the build does not depend on the frame rate.
- `createRenderApi(deps)` builds the `window.__swarmloom` object with your own loader and player factory. `deps.load` gets the frame height and the `terminalFont` init option too (`{ format, height, terminalFont? }`); for `fill` the loader has to build the terminal adapter with `createTerminalAdapter({ fill: true, viewportHeight: height })` (`@swarmloom/adapter-terminal`) itself, as the render page does. A loaded source with a live page (`LoadedHtml.live`) gets it shown on go live.
- `RenderSession` takes `live: true` to go live once the finale settles. Once it goes live (on its own or at a `live` cue), `done` waits for the stage to show the page (`PlayerOptions.onLive`) even past `tailMs`, at most 2.5 s after go live.

## In-browser export

`@swarmloom/export/browser` makes the CLI's video in a web page, with no screenshots and no share prompt. Studio's Export dialog uses it.

```ts
import { exportVideo } from "@swarmloom/export/browser";

const result = await exportVideo({
  input: { name: "notes.md", text },
  width: 1280,
  height: 720,
  fps: 30,
  settings: { seed: 1, theme: "light", sound: true },
  signal,
  onProgress: (p) => console.log(p.phase, p.frames, p.totalFrames, p.etaMs),
});
// result.blob is an MP4 (H.264) or WebM (VP9); result.extension says which.
```

- A hidden same-origin `<iframe srcdoc>` runs the render page (the code of `dist/render`) in its own window. The exporter calls `init()` and `step(1000 / fps)` in the CLI's order, so the same input, settings and seed give the same frames as `swarmloom render`. `settings` takes the `init` options other than input, size, fps, `cues` and `blueprint` (the same player settings as the CLI's; the in-page export has no cues and always loads `input`).
- The frame sees the media features of the CLI's browser at `--scale 1`, whatever the user's system settings, screen and input devices: no motion, transparency or contrast preference and no forced colours, `prefers-color-scheme: dark` for `theme: "dark"` and `light` otherwise (`auto` included), one device pixel per CSS px, an 8-bit sRGB standard-range screen (`color-gamut: srgb`, `dynamic-range: standard`) the size of the video (`device-width`, `device-height`), a mouse (`pointer: fine` and `hover: hover`, also for `any-pointer` and `any-hover`) and `display-mode: browser`. `devicePixelRatio` is 1, `matchMedia` answers with those values, the frame's document takes only that color scheme, and while the host differs the tests of those features in the frame's style sheets (the stage, the HTML adapter's page) are rewritten to their answers. Reduced motion in an export is the `reducedMotion` setting only. Not pinned: images chosen by `srcset` or `<source media>`, and the `image-set()` option the frame loads (the frames draw the option the CLI shows); `screen` and `navigator.maxTouchPoints` as scripts read them; the browser's own colours (default text, form controls) in a page that takes both schemes with `color-scheme: light dark`, which follow the system; and text anti-aliasing, which Chromium adapts to a high-density screen, so frames from such a screen can differ slightly in text edges.
- Each frame is serialised into an SVG `<foreignObject>` image (computed styles inlined, shadow roots and same-origin iframes flattened, images and fonts embedded as data URLs, each resource at most once for image elements and once for CSS however often it is used, a large photo in an `<img>` halved as often as its box allows; of the web fonts, only the faces the frame's text can use, by weight, style, stretch and `unicode-range`, each once however many sheets declare it, read and encoded once per export), drawn into a canvas and handed to the encoder; a frame whose image comes out the same as the last one's draws that one again, and while the page holds still, as during an opening or after going live, a frame is not serialised at all: the last image is drawn again under the cursors. Nothing in the page is wrapped or intercepted to tell: since the last frame, no DOM mutation, load or popover toggle happened in the page or in the live page it went live to (which is not watched while it waits out of view before going live, nor are its font faces drawn), and these read the same again: which style sheets apply and the text of every rule in them (so a rule edited through the CSSOM counts however it was edited; a font face counts without its source, which changes only by loading), focus (the focused element, whether it matches `:focus-visible`, and whether the document has focus), fonts, scroll offsets, the size of every box written empty, the pixels of every canvas drawn into the image, and what each Web Animation shows (its iteration progress and keyframes, a CSS animation's through the text of its rule, so seeking one that holds its end state changes nothing); a video, a frame of another origin, an SMIL animation or an image still loading that lays out a box (an `<img>`, or a CSS `content`, `list-style-image` or `shape-outside` image, which fires no event once it has loaded, also in a box left out or written empty away from the viewport, which it may grow into view; there a list item's `list-style-image` is read only while a marker image the page's CSS names still loads or cannot be told from the CSS, as in a style sheet of another origin or through `var()`, since each item would read an inlined bullet's whole data URL again) makes every frame walk. Reading the rules back costs about 3 µs a rule in Chromium, so a still frame takes about 1.7 ms at 1280x720 on the examples and about 18 ms on a page with 5,000 rules; after two frames in a row that changed (a mutation, a load, a scroll, an animation that shows something else, as while the stage builds or after going live, where every frame seeks the animations) the next frame leaves the rules unread. The engine takes some state at its rendering updates, from the layout and scroll offsets it sees then (scroll-state container queries, the scroll offsets and fallbacks of anchor positions, whether a `content-visibility: auto` box is relevant, scroll and view timelines, the link or scroll marker a scroll spy marks `:target-current`, whether a `::scroll-button()` is disabled), so it shows a change there only at the next one, with no mutation or event. The scroll offsets between an anchor-positioned box's anchor and its containing block move the box after layout, so its computed insets leave them out, as they leave out the cell of a `position-area`: the walk moves the box's clone to where the page draws the box, unless a box it is in transforms or zooms it, its own transforms do more than move it in 2D or its containing block is one the walk cannot be sure of; there, and for pseudo-elements, the box stays where its insets put it. On a page whose CSS uses one of those (in a style sheet that applies or a `style` attribute of the page, or of the live page while it waits out of view, or in a style sheet of another origin, whose rules cannot be read; not in a sheet switched off or for other media, as the Studio sheets its export frame mutes), a frame that walks after a change first waits for that update, as the CLI's screenshot comes after it: up to a display frame (1 s at most where the browser runs no animation frames), about 4 to 8 ms a walk in headless Chromium at 1280x720, so such an export takes about 7 to 19% longer where most frames walk (a spinner, a live tail), with the same frames; after going live, a page with scroll-state queries, `position-try` fallbacks or scroll-spy selectors also waits in each step (see go live above), about 40% longer in all on a 200-card page with a spinner that goes live at 4 s. Other pages, the examples among them, walk at once; telling costs about 0.4 ms a walk per 1,000 elements with a `style` attribute. Either way the next frame walks again after the update that follows and holds once a walk gives the same markup, so a still stretch starts with one more walk. A hidden tab takes no rendering updates: there a frame walks at once, and that state stays as the engine last took it until the tab shows again. Only what can show is written: subtrees more than 256 px away from the viewport are left out (out of flow) or written as empty boxes of their size with only the properties that size and place them (in flow: the sections, headings, paragraphs and quotes of a long live page, with the margins their content shares with them, inside `display: contents` or inline wrappers too, inline blocks aligned by their top, middle or bottom, and the cells of table rows away from the viewport), and boxes under a frame that covers the whole viewport are left out. A box away from the viewport is written as the last frame wrote it while nothing in it, around it or in the sheets (the text of their rules) changed, it kept its size and margins (margins in percentages or container units follow the boxes around it) and it stayed away, without being read again, and a run of such boxes one after another in block flow (the sections or cards of a long live page) is written as one empty box, so the image of a long live page with one animation running, and the time to decode it, stays about what a short one's is; the walk still passes each box away from the viewport, about 1 ms per 100 in Chromium, and list items, flex and grid items and boxes a transform moves are written one each, so they add to the image. An animation counts as a change only on frames where it shows something else (other keyframes, or another iteration progress). Exceptions, where the far boxes are read again on such frames: the animation transforms, filters or recolours the text of an element they are in (a transform on a wrapper), or it changes layout while a style sheet queries container sizes (container rules or units) or cannot be read (another origin's); after a layout change, so are the far boxes holding something positioned against a box outside them, and those in block flow after a float. SVG elements with an id inside what is left out (the clip paths and gradients of an exported icon, a symbol) are written on their own, drawn nowhere, when something written refers to them. The canvases painted last (the cursor layer, and a WebGL model under it) are drawn over the image instead of being encoded into it as PNGs. Text a page does not write itself (a counter or list marker in a script its text does not use) can fall back to another font when the web font is split by `unicode-range`. Apart from that state in a hidden tab, nothing depends on wall time. With `hashFrames: true`, `result.frameSha256` holds the SHA-256 of every frame's RGBA pixels before encoding, so two runs can be compared; it costs a readback per frame, so it is off by default. The encoded files can still differ: Chromium's encoders do not write the same bytes on every run, though the decoded frames look the same.
- WebCodecs encodes H.264 when `isConfigSupported` accepts it at this size, else VP9; [Mediabunny](https://github.com/Vanilagy/mediabunny) (MPL-2.0, used unmodified) writes the MP4 or WebM. Timestamps come from the frame index. Encoded frames wait in `Blob` parts, outside script memory, and at the end the file is muxed with the soundtrack straight into `Blob` parts, so the video does not pile up in script memory however long it is. The MP4 reserves room for its index ahead of the media (fast start, as from the CLI), a few dozen bytes per frame at most.
- Sound: the run's sound log rendered with `OfflineAudioContext` in one piece, as the CLI renders it (about 23 MB of samples per minute, held while they are encoded), encoded as AAC or Opus. When neither encoder exists the video is silent, `result.soundUnsupported` is true and a warning says so.
- The loop yields to the event loop after every frame, and the snapshot of a frame pauses every few milliseconds (starting over when the page changed meanwhile), so the page stays responsive; `signal` cancels between frames and at those pauses; while the hidden frame is still starting or loading the input, it removes the frame at once. Without WebCodecs `exportVideo` throws `UnsupportedExportError`; `hasWebCodecs()` checks first.
- `maxDurationMs` (default 10 minutes) caps a build that never ends; `result.finished` is false then.

Limits of the snapshot: custom `::marker` and `::first-letter` styles are not reproduced, `position: sticky` does not stick, WebGL canvases show what reading them back returns at capture time (`drawImage()` when drawn over the image, `toDataURL()` when something paints over them), cross-origin images and videos without CORS are left blank (with a warning), a video's native controls are drawn as a likeness of Chromium's, and ink reaching more than 256 px past the boxes of a subtree away from the viewport (a huge shadow, a fixed-position pseudo-element) is not drawn.

The frame loads one of this package's modules as a module script. In a bundled app that module shares chunks with the app's entry, so the entry must not start the app inside the frame: check `isExportFrame()` first. Style sheets a bundler's preloader links into the frame are switched off.

## Quick recording

`recordElement(element, { mimeType?, fps?, videoBitsPerSecond?, audio?, signal? })` records an element live. It must be called from a click handler. It asks the user to share the current tab, crops the capture to the element (Element Capture, else Region Capture), mixes in audio and encodes with `MediaRecorder` (WebM, or MP4 where WebM is unavailable).

The `audio` option takes `"tab"` (default), an `AudioNode`, a `MediaStream` or `false`. Call `stop()` to finish, or read `result`, which also settles when the user stops sharing.

This is a real-time recording, not a deterministic export. `canRecordElement()` reports support. Failures throw a `RecordingError` with code `unsupported` (the message points to `npx swarmloom render`), `denied`, `wrong-surface` or `failed`.
