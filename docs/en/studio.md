# Studio

::: info Current status
Studio is online at the address below, and **Export in this browser** works in browsers with WebCodecs. The command from **Render with the command line** needs the `swarmloom` CLI, which is not on npm yet; build it from source for now (see [CLI](./cli.md)). This page describes v1 behaviour.
:::

Studio is SwarmLoom's browser workbench and an installable PWA. Address:

[https://boulea7.github.io/swarmloom/studio/](https://boulea7.github.io/swarmloom/studio/)

It is intended for files, pasted text, public URLs and examples. It does not replace the extension's access to the current tab's DOM.

## Home

The home screen offers four entry points:

- **Drop or open a file** in one of the [supported formats](./formats).
- **Paste** a small Markdown, SVG, HTML or source-code input; Jupyter notebooks, terminal recordings (asciicast) and patches are recognised by their content.
- **URL** to request a remote file or page.
- **Example gallery** with one licence-cleared sample per format, playable on click.

Adapters load on demand. The first use of a format may fetch its module; cached modules can work offline.

Back and Forward in the browser reopen each step's own local file. A tab keeps the last 8 local files; older entries ask you to pick the file again. Changing the interface language does not interrupt what is playing and keeps any URL or pasted text on the home screen that was not opened yet.

## Player

The player uses an inline stage with its own scrolling content. Its settings drawer includes:

- Cursor count, speed and labels;
- Light and dark themes;
- Sound toggle, sound pack and clicks on the beat;
- `flock`, `halo` and `none` finales;
- Intro: the icon, or outline first;
- Show the original first (1.5 s of the finished content, then the build) and back to the top at the end;
- Reduced motion;
- Interface language.

Below the stage, the progress bar becomes a time line you can drag when the player can seek. Once the build is playing, drag it anywhere; arrow keys move 2%, Page Up/Down 10%, and Home/End jump to the start or the end. The count beside it shows the layers built.

Phones use a bottom settings sheet. Watch mode omits full settings and keeps only the minimum viewing controls.

## URL parameters

| Parameter | Purpose |
| --- | --- |
| `?example=<id>` | Open a bundled example |
| `?src=<url>` | Open a URL-encoded remote source |
| `#d=<payload>` | Open small text content compressed into the hash |
| `?autoplay=1` | Play after loading; sound still follows browser gesture policy |
| `?watch=1` | Use the small, round-safe viewing layout |
| `?import=1` | Highlight the file picker (links from the extension); keeps the normal home screen even on a watch-sized screen |

`#d=` uses deflate-raw and base64url and should be generated by Studio rather than assembled by hand. A hash is not sent with an ordinary HTTP request, but anyone receiving the link can still read it.

## Offline use

The hosted Studio registers a Service Worker on the first visit, whether or not you install the PWA. It caches the app shell and, in the background, fetches every format's adapter chunks and the in-browser video exporter, together with what they import (a few megabytes; for PDF, only the pdf.js build this browser runs). Local files, cached examples and existing scenes can then run offline, in a browser tab or in the installed app. The worker's version is a hash of the content of every cached file, so a change to only the page, the manifest or an icon still reaches cached tabs and installed copies.

Offline mode does not make remote URLs readable. Adapters the worker has not fetched yet, uncached remote resources, external fonts and model dependencies still need a network. Clearing site data removes the cache.

## System sharing and file handlers

On supported Chromium platforms, an installed PWA can register through its manifest:

- `share_target` for text, URLs or files from system sharing;
- `file_handlers` as an open-with target for supported extensions.

These are not universal capabilities. iOS and other platforms retain copy, paste, file selection and outbound system sharing as alternatives. Installing the PWA does not give Studio access to another tab's cookies, authenticated state or DOM.

## Remote URL limits

Studio fetches URLs directly in the browser, so same-origin policy, CORS, mixed content and site permissions still apply.

- Public files that allow browser reads can be imported directly.
- Knowing the URL of an authenticated page does not make it readable.
- Studio has no default server proxy and does not ask for your cookies.
- Use the extension in the original tab when you need its authenticated live DOM.
- Use the CLI's local browser workflow for fixed-viewport, unattended capture.

The remote site may log requests. Opening only a local file does not upload its content.

The Studio page carries a Content-Security-Policy that backs up every format's sanitizer: only Studio's own scripts run, and from the web only https images, fonts and the file you open load. Turning off **Load web images and fonts** adds a stricter policy that blocks web images and fonts too, and exporting in the browser does not request them either; turning it back on needs a page reload, which Studio offers.

## Foldables and small screens

Studio always has an ordinary responsive layout. Supported Chromium environments can add dual-screen enhancements through Viewport Segments:

- Horizontal dual screen: the full stage on one segment, settings and dialogs on the other.
- Vertical dual screen: stage above, controls and dialogs below.
- Fold or rotate: recompute presentation without resetting the seed or timeline.

`?watch=1` or a watch-sized screen (up to 320 × 400) uses the tiny player; a narrow window on a bigger screen and `?import=1` links keep the normal Studio. It shows a static poster first, is muted by default, draws no rulers or size badges, and has a large play button, progress and **Open on phone**. Its QR code opens the same item on the phone with the same speed, intro, show-the-original-first and other build settings, but not the watch's own fewer cursors and silence. While a build plays or is paused, the controls sit small along the bottom and fade soon after you start or resume. With `?round=1` the stage and the controls stay inside the square that fits the circle, so the circle never crops the text; the title keeps to one line and is left out on faces under about 175 px, and on the smallest faces the buttons shrink to fit. It does not depend on poorly supported round-display media queries.

## Export and sharing

**Export** (shortcut `E`) opens one dialog for both ways to make a video. Pick the size (1280 × 720, 1920 × 1080, 1080 × 1920 or 1080 × 1080), 30 or 60 fps, and whether to include sound.

- **Export in this browser** renders the video in the page, frame by frame. A hidden frame runs the same render page as `swarmloom render`, advances the same virtual clock by whole frames and keeps the same tail, so the frames match the CLI's for the same settings. Each frame is drawn from a snapshot of the page, encoded with WebCodecs (H.264 in MP4, or VP9 in WebM when H.264 is not available) and packed by [Mediabunny](https://github.com/Vanilagy/mediabunny). The sound is the run's sound log rendered offline, as AAC or Opus; when the browser cannot encode either, the video is silent and the dialog says so. A progress bar shows the frame count and the time left, **Cancel** stops at once, and **Download** saves the file. The page stays usable while it works; keep the tab open. While the export runs with the dialog open, the preview pauses so the export has the main thread; it plays on when the export ends or the dialog closes.
- **Render with the command line** shows the `swarmloom render ...` command for the same file, with the chosen size, frame rate, theme, language, sound and web images setting, and the same 10-minute length limit (`--max-duration 600`; the CLI's own default is 120 s). It also offers WebM, GIF and WebP. The browser knows an opened file's name but not its folder, so the command names the file alone and the dialog says to run it in the folder that holds the file; pasted or shared text has to be saved under the given name first. The command runs the `swarmloom` CLI on your PATH (`npm install -g swarmloom`) and downloads nothing; `npx swarmloom` would fetch and run whatever package holds that name on the registry.

Browsers without WebCodecs (no `VideoEncoder`) show only the command. The exporter and Mediabunny are not part of Studio's start-up: the page loads them when the dialog first opens. In the hosted Studio, the Service Worker has usually downloaded them already, in the background after the first visit, with the format adapters (see Offline use above).

Limits of the in-page export:

- It takes about 0.1 to 0.2 s per frame at 1280 × 720, so a 35 s video takes about 3 minutes; live pages with thousands of elements take longer. Input stays responsive while it works: each frame's snapshot pauses every few milliseconds, and drawing a frame holds the page for at most about a tenth of a second, longer when the web fonts the page's text uses add up to megabytes (about 40 ms per MB in Chromium).
- Frames are drawn from an SVG snapshot of the page, not a screenshot. Custom `::marker` and `::first-letter` styles, `position: sticky`, WebGL canvases, native video controls (drawn as a likeness), images from other sites (not requested again, as that would send those sites Studio's address) and cross-origin videos that do not allow CORS (both left blank; the dialog says how many) can differ from the CLI.
- It uses the sound pack chosen in Studio; the CLI always uses the default pack.
- Encoders differ: Chromium tags its H.264 as BT.601, the CLI writes BT.709, so decoded colours can differ by a few levels. Chromium on Linux has no AAC encoder, so MP4 files there carry Opus sound, whose track runs up to 20 ms past the video.
- Like the CLI, the export ignores the system's reduced-motion, reduced-transparency, high-contrast (Windows forced colours) and increased-contrast settings, the screen's pixel density, size, colour gamut and HDR, a touch screen, and Studio running as an installed app: pages and 3D models build with full motion and their own colours, at one device pixel per CSS pixel, as on an sRGB desktop screen with a mouse. Images a page picks with `srcset` or `<picture>` still follow the screen, with high contrast on, system colour keywords such as `Canvas` still take the system's palette, and on a high-density screen the browser can anti-alias text edges a little differently, so frames can differ slightly from the CLI's and from exports made on other screens.
- Two exports of the same input and seed on the same screen draw the same pixels in every frame, but the browser's encoder does not write the same bytes each time. The difference is too small to see.

**Share** can put small text into `#d=`. The extension's Studio opens only in the browser that has the extension, so its links point at the hosted Studio, and the text of a local file (a `file://` address) goes into `#d=` as well. Export a video or share the original file for large content. Check for sensitive material before sharing.

## Studio inside the extension

The release build (`pnpm build:extension`) bundles the same Studio build into every extension package. It opens PDF, document, image and model links, and restricted pages through the notice page. Local builds made with `--without-studio` send these links to the hosted Studio instead.

Extension mode uses relative assets and does not register a Service Worker. It keeps the same format pipelines and privacy boundaries without contacting a separate SwarmLoom service.
