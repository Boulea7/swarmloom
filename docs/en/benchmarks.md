# Benchmarks

`pnpm bench` plays the demo page and a synthetic page of about 4,400 layers in headless Chromium. It records snapshot time, build frame rate, per-frame script cost, long tasks, mounted stage nodes and heap, and checks them against the budgets in `scripts/bench/lib.mjs`. The design targets are on [Performance](./performance.md).

- **Snapshot**: total time of `snapshot()`. The walk runs in slices of about 10 ms, so the page stays responsive meanwhile; a separate budget on the longest task during the 4k-layer snapshot fails when the walk blocks the page in one long task again.
- **rAF callback**: script time of all `requestAnimationFrame` callbacks in a frame, summed.
- **Stage nodes**: elements mounted in the player's isolated stage.
- **Heap**: used JS heap after a forced GC, including the engine code the bench loads.

## Scenarios

The script bundles the engine and the DOM snapshot from source with esbuild and runs, one after the other, at 1280×800, DPR 1, sound off:

- **Demo page**: `examples/web/demo.html`. After the snapshot it builds fully with `agents: "auto"` and seed 1, replays three times at triple speed to see whether the heap grows, then times `seek(0)` followed by `seek(10 s)`, a replay from the start (after the replays the run is past 10 s, so a lone forward seek would only fast-forward its tail).
- **Synthetic 4k-layer page**: 980 cards, about 4,400 layers. It measures the first 8 s of the build, then calls `finish()` and counts mounted nodes. Last, it switches to `follow: "tour"`, times `seek(0)` followed by `seek(60 s)` and counts the stage nodes after it: the tour camera moves across the page while the seek fast-forwards.
- **128-cursor flock**: the demo page with 128 cursors; after `finish()` reaches the flock finale, the pointer sweeps for 3 s.

The console output also prints one observation of the reference product on its own demo page (different page, machine and method), for orientation only; it never decides a pass or a failure.

## Budgets

The budgets are loose on purpose. They catch structural regressions: a snapshot that turns into one long task, `finish()` mounting every layer at once, replays leaking memory, per-frame cost doubling. They are not the design targets. `pnpm bench` exits with status 1 when any budget fails.

Timing budgets assume nothing else competes for the CPU: run the bench alone on an idle machine.

## Commands

```bash
pnpm bench                                   # run the three scenarios and check the budgets
node scripts/bench.mjs --report-only         # print the results, exit 0 even when a budget fails
node scripts/bench.mjs --write               # write the results table into this page and the Chinese one
node scripts/bench.mjs --json bench.json     # also save the raw results
node scripts/bench.mjs --json > bench.json   # raw results on stdout, the readable report on stderr
node scripts/bench.mjs --chrome /path/to/chromium
```

The browser is taken from `--chrome`, then `$SWARMLOOM_CHROME`, then `~/bin/chromium`, then Playwright's bundled Chromium. Unit tests for the budget and table logic: `pnpm test:bench`.
